## Cross-cutting findings that change the plan

1. **Visible-devices ID space (item 11).** Integers are positions in the BDF-sorted list of `/dev/tenstorrent/*`, equal to the UMD logical chip id of the unfiltered cluster. They are not the `/dev` numbers; on a Galaxy the two can differ arbitrarily (a documented 8-chip example maps UMD chip 0 to `/dev/tenstorrent/2`). Use full BDF tokens, which fail closed on typos. The BDFs of `/dev/tenstorrent/16..23` are not in the brief and not derivable from source.
2. **"Only 16..23 are ever opened" cannot be guaranteed by `TT_VISIBLE_DEVICES` alone.** UMD's enumeration `open()`s every existing `/dev/tenstorrent/N` node (read PCI info by ioctl, then close), once or three times per `enumerate_devices()` call and from several callers; a post-open `/proc/self/fd` check passes anyway because those fds are closed. A source comment says tt-kmd messages the chip's firmware on every `open()`. Only OS-level isolation (container exposing 8 nodes, or permissions that make the other nodes un-openable) gives a hard guarantee. This conflicts with the brief's rule 2-1/2-2 and needs an owner decision.
3. **`import ttnn` is impossible with the current build** (no `_ttnn.so`; no `ttml` either). A Python-bindings build is a new build and the in-tree install step writes into the source tree; plan a separate build dir plus an overlay.
4. **fp32 matmul = TF32 multiplies + fp32 accumulation** (no UnpackToDest for matmul operands). This is the largest numerical risk for parity tolerances; measure first (Q10).
5. **Row gather must use `ttnn.gather`/`ttnn.tosa_gather`** (fp32 table, UINT32 index). `ttnn.embedding` hard-requires a bf16 table.
6. **Trace freezes Python scalars and RNG seeds**: Adam lr / bias-correction and PPO adaptive-LR must be device tensors; noise must be sampled outside the trace (the brief's parity mode already does this on the host).
7. **One tray, one process:** with `TT_VISIBLE_DEVICES` restricted to the tray and a single process, metal's control plane auto-discovers the mesh (2x4 first candidate for 8 chips); a `1x8` request on a 2x4 system mesh is placed in ring order. Fabric on a tray subset is the main hardware unknown (Q3).
8. **Docs vs code:** the tech reports say `TT_VISIBLE_DEVICES` uses `/dev/tenstorrent/<id>`; the code and tt-metal's own tests say BDF-sorted/logical. Several docstrings understate fp32 support (tests show it works); one doc (`ttnn.all_reduce`) does not say how fp32 is reduced.

## 1. matmul / linear and the compute kernel config

Names verified: `ttnn.matmul`, `ttnn.linear`, `ttnn.addmm`, `ttnn.init_device_compute_kernel_config`, `ttnn.WormholeComputeKernelConfig`, `ttnn.DeviceComputeKernelConfig`, `ttnn.types.BlackholeComputeKernelConfig` (alias), `ttnn.MathFidelity`, `ttnn.ThrottleLevel`, `ttnn.CoreGrid`, `ttnn.MatmulMultiCoreReuseProgramConfig`, `ttnn.MatmulMultiCoreReuseMultiCastProgramConfig`, `ttnn.MatmulMultiCoreReuseMultiCast1DProgramConfig`, `ttnn.MatmulMultiCoreReuseMultiCastDRAMShardedProgramConfig`.

**Signatures as bound**
- `ttnn.matmul(input_tensor_a, input_tensor_b, *, transpose_a=False, transpose_b=False, memory_config=None, dtype=None, program_config=None, activation=None, compute_kernel_config=None, core_grid=None, output_tile=None, optional_output_tensor=None, global_cb=None, sub_device_id=None, prefetcher_pipes=[])`: `OP/matmul/matmul_nanobind.cpp:824-841`.
- `ttnn.linear(...)`: same plus keyword `bias=None` first and `in0_column_offset=None` last: `matmul_nanobind.cpp:903-922`.
- `ttnn.addmm(input_tensor, mat1_tensor, mat2_tensor, *, alpha=1.0, beta=1.0, memory_config, dtype, program_config, compute_kernel_config, core_grid, output_tile, optional_output_tensor)`: `matmul_nanobind.cpp:1058-1072`.
- Program-config constructors: Reuse `(compute_with_storage_grid_size, in0_block_w, out_subblock_h, out_subblock_w, per_core_M, per_core_N)` (`matmul_nanobind.cpp:62-78`); MultiCast 2D adds `out_block_h/out_block_w, transpose_mcast, fused_activation, fuse_batch` (`:152-196`); MultiCast1D adds `mcast_in0, gather_in0, hop_cores, untilize_out, ...` (`:348-407`); DRAMSharded `(in0_block_w, per_core_M, per_core_N, fused_activation)` (`:566-573`).

**Dtypes, layouts, restrictions**
- Inputs and bias: BFLOAT8_B, BFLOAT4_B, BFLOAT16 or FLOAT32, TILE layout only (`matmul_nanobind.cpp:778-789, 856-875`; `OP/matmul/device/matmul_device_operation.cpp:49-61`). Inner tile dim must be 32 (`:52-57`).
- Non-tile-aligned logical K works (fp32, K=100, padding poisoned with -42, PCC >= 0.999): `MT/test_matmul.py:3731-3750`.
- Output dtype = `dtype` arg, else `optional_output_tensor` dtype, else input_a dtype (`matmul_device_operation.cpp:3170-3183`). `core_grid` and `program_config` are mutually exclusive (`:3150`). Default output memory is DRAM interleaved (`matmul_nanobind.cpp:758`).
- `activation` is a string or `ttnn.UnaryWithParam`; not allowed with sharded inputs, use the program config's `fused_activation` (`OP/matmul/matmul.cpp:238-243`; `matmul_nanobind.cpp:761`). The accepted strings are in `OP/eltwise/unary/common/unary_op_utils.cpp:994-1111`; there is NO "elu" string. "exp"/"log" fuse the approximate variants (`unary_op_utils.cpp:1031-1039`), "tanh" the accurate one (`:1043-1045`).
- Batching: A with batch dims times a B without batch dims (3D x 2D weight) broadcasts B (`matmul_nanobind.cpp:697-700`); tests `MT/test_linear.py:34-36` (`(1,m,k) x (k,n)`) and `:295-296` (`(B,1,m,k) x (k,n)`). Bias is normally `[1,N]` (`matmul_nanobind.cpp:882-885`); rank-1 `(n,)` is exercised at `MT/test_linear.py:1235-1262`. Otherwise the bias is a separate add (`OP/matmul/matmul.cpp:131-203`).
- Transpose flags are supported; if the chosen program config cannot handle them the op inserts `ttnn::transpose` itself (`matmul.cpp:286-293`). Examples: `transpose_a` `MT/test_matmul.py:2434-2444`; `transpose_b` + bias `MT/test_linear.py:1256`.

**Compute kernel config (fields, constructors)**
- `ttnn.WormholeComputeKernelConfig(*, math_fidelity=MathFidelity.Invalid, math_approx_mode=True, fp32_dest_acc_en=False, packer_l1_acc=False, dst_full_sync_en=False, throttle_level=NO_THROTTLE)`: `ttnn/cpp/ttnn-nanobind/operations/core.cpp:70-84`; all fields read/write (`:85-113`); struct `OP/core/compute_kernel/compute_kernel_config.hpp:19-27`. One class serves both architectures: `ttnn/ttnn/types.py:60-61`; `ttnn.types.BlackholeComputeKernelConfig` is an alias and is NOT in the top-level import list (`ttnn/ttnn/__init__.py:278-280`); usage `tests/ttnn/nightly/unit_tests/operations/matmul/test_dram_sharded_then_1d_matmul.py:106`.
- `ttnn.init_device_compute_kernel_config(arch, device_kernel_config=None, *, math_fidelity=LoFi, math_approx_mode=True, fp32_dest_acc_en=False, packer_l1_acc=False, dst_full_sync_en=False, throttle_level=NO_THROTTLE)`: `core.cpp:120-132`; a passed-in config is returned unchanged, else one is built from the keywords (`compute_kernel_config.cpp:21-43`); `arch` is unused. Example `models/demos/deepseek_v3_d_p/tt/kda/recurrence.py:556-562`.
- `MathFidelity`: LoFi=0, HiFi2=2, HiFi3=3, HiFi4=4, Invalid=0xff (`tt_metal/api/tt-metalium/base_types.hpp:13-19`; exported `ttnn/cpp/ttnn-nanobind/tensor.cpp:60`).
- Pitfall: both constructors default `math_approx_mode=True` and the class defaults `math_fidelity=Invalid` (`core.cpp:79-80, 128`) while the matmul auto-default is approx False (`matmul_device_operation.cpp:3189`). Always set fidelity and approx mode explicitly. The effect of `Invalid` is unverified (emitted as a raw enum cast, `tt_metal/jit_build/genfiles.cpp:1152`).
- tt-train's own recipe, for reference: `fp32_dest_acc_en=true, math_approx_mode=false, HiFi4, packer_l1_acc=true` (`tt-train/sources/ttml/core/compute_kernel_config.cpp:7-35`).

**How fp32 accuracy is selected (defaults when you pass no config)**
- Fidelity: both inputs FLOAT32 => HiFi4 on Blackhole (HiFi3 on Wormhole, because of HW bug #38306); otherwise HiFi2 if no program_config and no core_grid, else LoFi (`matmul_device_operation.cpp:3137-3146`). `math_approx_mode=False`, `fp32_dest_acc_en = (output dtype == FLOAT32)`, `packer_l1_acc = !fp32` (`:3184-3191`). A user config REPLACES all of these.
- `dst_full_sync_en` only works with the 1D `gather_in0` path (`matmul_device_operation.cpp:610-621`). With `fp32_dest_acc_en`, `out_subblock_h*out_subblock_w <= 4` (`OP/matmul/device/factory/matmul_multicore_reuse_optimized_program_factory.cpp:91-95`); auto config respects this (`OP/matmul/device/config/matmul_program_config.cpp:190-203, 990-996`).

**fp32 numerics: the operands are TF32-class, the accumulation is fp32**
- Matmul reads in0/in1 through SrcA/SrcB (`unpack_modes = {IN0_DFB: UnpackToSrc, IN1_DFB: UnpackToSrc}`: `OP/matmul/device/factory/matmul_multicore_reuse_optimized_program_factory.cpp:594-607`, comment there: "Inputs are read via SrcA/SrcB"). `tech_reports/op_kernel_dev/accuracy_tips/accuracy_tips.md:142` states that on the FPU backend "FP32 operands pass through TF32 SrcA/SrcB even when destination accumulation is FP32". No UnpackToDest option exists for matmul operands in any matmul factory (searched). So a "fp32" matmul multiplies ~10-bit-mantissa operands (TF32) and accumulates in fp32; it will NOT match a torch fp32 GEMM bitwise. Magnitude not quantified in any test (`MT/test_matmul_fp32_partials_reload.py:11-12` deliberately uses bf16-representable inputs); this must be measured (Q10).
- Accumulation across K blocks is lossless with `fp32_dest_acc_en=True`: the fp32 partials buffer is reloaded with UnpackToDest (`matmul_multicore_reuse_optimized_program_factory.cpp:125-128, 339-344`); comment at `matmul_multicore_reuse_mcast_2d_program_factory.cpp:1736-1740` explains that without it partials would round to TF32 (10 mantissa bits) at every K-block boundary. Test: `MT/test_matmul_fp32_partials_reload.py:1-22` (rel max err <= 2e-4 at HiFi4 for bf16-representable inputs).
- The Wormhole-only fp32+HiFi4 bug does not apply to Blackhole (`matmul_nanobind.cpp:744-749`; `compute_kernel_config.cpp:45-67`).

**Examples:** fp32 in/out, HiFi4, program_config `MT/test_matmul_fp32_partials_reload.py:25-60`; linear with HiFi4 + fp32 acc + `core_grid` `MT/test_linear.py:377-402`; default-config fp32 matmul (very loose tolerance) `MT/test_matmul.py:3025-3043`.

**Verdict (item 1): yes, with a caveat.** fp32 in/out, fp32 bias and fp32 accumulation are supported on Blackhole (HiFi4 + `fp32_dest_acc_en=True`, `math_approx_mode=False`), but operands are rounded to TF32 inside the FPU, so expect ~1e-3-class relative error vs torch fp32; quantify before setting tolerances.

## 2. Elementwise unary and binary math

Names verified: `ttnn.elu`, `ttnn.elu_bw`, `ttnn.exp`, `ttnn.log`, `ttnn.sqrt`, `ttnn.rsqrt`, `ttnn.square`, `ttnn.reciprocal`, `ttnn.tanh`, `ttnn.neg`, `ttnn.pow`, `ttnn.add/subtract/multiply/divide` (+ aliases `sub`, `mul`, `div`, in-place `add_`, `subtract_`, `multiply_`, `divide_`, `sub_`, `mul_`, `div_`), `ttnn.rsub`, `ttnn.softplus`. `ttnn.unary_bw` does NOT exist (backward ops are per-op `*_bw`).

**ELU and its derivative**
- `ttnn.elu(input_tensor, *, alpha=1.0, memory_config=None, output_tensor=None, sub_core_grids=None)`: `OP/eltwise/unary/unary_nanobind.cpp:519-529` (template), `:1816-1817` (registration). SFPU kernel `alpha*expm1(x)` for x<0, fp32-aware (`tt_metal/hw/ckernels/blackhole/metal/llk_api/llk_sfpu/ckernel_sfpu_elu.h`). fp32 sweep passes ULP <= 1 (<= 2 for alpha 0.1): `ET/test_unary_category4_float32.py:202-228`. The docstring lists only bf16/bf8_b (`unary_nanobind.cpp:1817`); the fp32 test contradicts it.
- `ttnn.elu_bw(grad_tensor, input_tensor, *, alpha=1.0, memory_config=None)` returns a list: `OP/eltwise/unary_backward/unary_backward_nanobind.cpp:444-501, 1057-1063`. It is a composite: `where(gtz(x), grad, grad * (exp(x, false) * alpha))` (`OP/eltwise/unary_backward/unary_backward.cpp:807-823`, comment "result : grad * (torch.where(input > 0, 1, alpha * torch.exp(input)))"). Tests are bf16/PCC-only (`tests/ttnn/nightly/unit_tests/operations/eltwise/backward/test_backward_elu.py:30-37`); fp32 correctness untested. Equivalent to composing it yourself from `gtz`/`where`/`exp`.
- Matmul cannot fuse ELU by string (no "elu" in `unary_op_utils.cpp:994-1111`); a fused `UnaryWithParam(UnaryOpType.ELU, ...)` is listed in the include table (`unary_op_utils.cpp:30`) but untested.

- `ttnn.sum(input_tensor, dim=None, keepdim=False, *, memory_config=None, compute_kernel_config=None, scalar=1.0, correction=None, sub_core_grids=None, fast_and_approximate_mode=False, output_layout=None)`: `OP/reduction/generic/generic_reductions_nanobind.hpp:172-186` (re-verified).

**Dtypes, layouts, limits**
- FLOAT32, BFLOAT16, BFLOAT8_B in TILE; FLOAT32 and BFLOAT16 also in ROW_MAJOR; INT32 for sum/min/max but not mean (`generic_reductions_nanobind.hpp:29-35, 72-83`). Output dtype = input dtype (`reduce_op.cpp:505`). Rank > 4 is squeezed to 4D, rank < 4 unsqueezed (`generic_reductions.cpp:280-282`). std/var need TILE and rank >= 2 (rank 1 reshaped to `[1,N]`) (`generic_reductions.cpp:413-415`; `OP/reduction/generic/device/welford_reduce_device_operation.cpp:36-53`).
- A single reduction along dim -1, -2 or (-2,-1) is one device op; any other dim set is decomposed axis by axis with `ttnn.transpose` (`generic_reductions.cpp:181-262`). The fast NC path exists only for bf16/bf8_b, never fp32 (`:482-488`).

**Batch axis vs whole tensor**
- For `[N, D]`: `dim=0` -> H-reduce (`REDUCE_COL`), `dim=-1` -> W-reduce (`REDUCE_ROW`), `(0,1)`/None -> HW (`REDUCE_SCALAR`) (`generic_reductions.cpp:264-273`; defines `OP/reduction/generic/device/reduce_op.cpp:22-41`). Factories `reduce_op_multi_core_h|w_program_factory.cpp`, `reduce_op_single_core_hw_program_factory.cpp`; kernel `kernels/compute/reduce.cpp:18-65`. With the accurate fp32 path an HW reduce is split into W then H (`reduce_op.cpp:249-256`). Tall inputs use a two-stage H-reduce with FP32 partials (`reduce_op.cpp:353-496`).
- Global grad norm = `ttnn.sum(ttnn.square(g))` then sqrt. Test pattern for a full sum: `tests/ttnn/unit_tests/operations/reduce/test_sum.py:49-80`.

**fp32 accumulation**
- `compute_kernel_config=None` => HiFi4, approx off, `fp32_dest_acc_en=True` (`reduce_op.cpp:144-153`); an fp32 input then takes the accurate SFPU path with full fp32 accumulation (`:197-208`). The FPU path truncates fp32 inputs to TF32 and is used if `fast_and_approximate_mode=True` or your config has `fp32_dest_acc_en=False` (`generic_reductions_nanobind.hpp:44`; `reduce_op.cpp:197-199`).
- A user config REPLACES the default; the Python constructor defaults are `fp32_dest_acc_en=False, math_approx_mode=True, math_fidelity=Invalid` (`ttnn/cpp/ttnn-nanobind/operations/core.cpp:70-84`). So pass either `None` or an explicit `WormholeComputeKernelConfig(math_fidelity=HiFi4, math_approx_mode=False, fp32_dest_acc_en=True)`.
- std/var with fp32 input throw if `fp32_dest_acc_en=False`; with None they default to true (`welford_reduce_program_factory.cpp:145-153`; `welford_reduce_device_operation.cpp:136-141`). fp32 mean is lowered to SUM then a multiply by 1/N (`reduce_op.cpp:234-239`). `ttnn.min` rejects `fast_and_approximate_mode=True` for fp32 (`generic_reductions.cpp:773-776`).

**Tile padding:** every reduce first calls `fill_implicit_tile_padding` with the identity (0 for sum/mean, -inf for max, +inf for min) (`generic_reductions.cpp:94-118, 569-576`), so unaligned N is safe (tests poison padding with -42: `test_sum.py:15, 59`); std/var use the logical H and W (`welford_reduce_program_factory.cpp:25-30, 58-63`). Cost: one extra pad-fill op per call. Non-reduction ops may leave arbitrary values in TILE padding.

**Dedicated global-norm ops:** `ttnn.moreh_norm(input, p, *, dim, keepdim, output, memory_config, compute_kernel_config)` and `ttnn.moreh_clip_grad_norm(inputs, max_norm, norm_type=2.0, error_if_nonfinite=False, *, total_norm=None, memory_config=None, compute_kernel_config=None)` (scales inputs in place) exist (`OP/moreh/moreh_norm/moreh_norm_nanobind.cpp:38-49`; `OP/moreh/moreh_clip_grad_norm/moreh_clip_grad_norm_nanobind.cpp:68-86`) but are BFLOAT16-only (`moreh_helper_functions.hpp:149-156` default `check_tensor` list `{BFLOAT16}`; `moreh_norm_device_operation.cpp:35`; `moreh_clip_grad_norm_step1_device_operation.cpp:17,20`), and `error_if_nonfinite` reads the result as bf16 (`moreh_clip_grad_norm.cpp:115-124`). `moreh_sum` is bf16/int32 only (`moreh_sum_device_operation.cpp:47-48`). tt-train's `clip_grad_norm` just calls that op (`tt-train/sources/ttml/core/clip_grad_norm.cpp:14-32`) and its test is bf16. Compose the norm from `square`, `sum`, `sqrt`, `multiply` instead.

**Verdicts (item 4):** `sum`, `mean`, `max`, `min`, `std`, `var`: **yes** (TILE fp32, default or explicit fp32-acc config, `keepdim=True`). `prod`: yes (unlikely needed). `moreh_norm`/`moreh_clip_grad_norm`: **no** (bf16 only).

## 6. Random numbers

**Names verified:** `ttnn.rand`, `ttnn.randn`, `ttnn.uniform`, `ttnn.bernoulli`, `ttnn.manual_seed`, `ttnn.experimental.dropout`; `ttnn.sin`, `ttnn.cos`, `ttnn.log`, `ttnn.sqrt` accept FLOAT32 (`unary_nanobind.cpp:1481-1486, 1675-1680, 1757, 1783`). `ttnn.normal`: NOT FOUND.

**`ttnn.randn`: true standard normal**
- `ttnn.randn(shape, device, *, dtype=bfloat16, layout=TILE, memory_config=DRAM, compute_kernel_config=None, seed=None)`: `OP/randn/randn_nanobind.cpp:53-64`. Box-Muller inside the kernel (two uniforms -> log, sqrt, cos, sin): `OP/randn/device/kernels/compute_standard_normal.cpp:86-101`. FLOAT32 and BFLOAT16, TILE and ROW_MAJOR (`randn_device_operation.cpp:10-18`; `randn.cpp:23-27`). No mean/std arguments: use `mean + std * randn`.
- Seeds: `seed=None` uses a persistent `mt19937(random_device)` that advances each dispatch (`randn_program_factory.cpp:24, 116, 132, 158-166`; test `tests/ttnn/nightly/unit_tests/operations/rand/test_randn.py:234-246`); an explicit seed builds a fresh `mt19937(seed)` per call, so the same seed reproduces the output (`test_randn.py:249-253`). The seed is a runtime arg excluded from the program hash (`randn_device_operation.cpp:47-52`): a new seed per call does not recompile.
- Mesh: `create_descriptor`/`override_runtime_arguments` ignore the mesh coordinate (`randn_program_factory.cpp:42-45, 146-151`); the adapter builds one program per coordinate range (`ttnn/api/ttnn/mesh_device_operation_adapter.hpp:608-618`). Inferred (not tested): all chips in a range get the same per-core seeds, hence identical samples. Do not expect decorrelated noise per chip from `randn` on a mesh.
- Trace caveat (Agent C inference): seeds are runtime args refreshed only in the cache-hit override path (`randn_program_factory.cpp:130-133, 152-165`), so a REPLAYED trace emits the same noise each replay: sample noise outside the trace or feed it in.

**`ttnn.rand`: uniform**
- `ttnn.rand(shape, device, *, dtype=bfloat16, layout=TILE, memory_config=DRAM, low=0.0, high=1.0, seed=0, mesh_mapper=None)`: `OP/rand/rand_nanobind.cpp:67-80`. FLOAT32/BFLOAT16 generated natively in `[low, high)`; other dtypes via fp32 + typecast (`rand_nanobind.cpp:21-30`; `rand.cpp:85-86`). Uniform on a 31-bit grid with a decorrelated lane salt (`tt_metal/hw/ckernels/blackhole/metal/llk_api/llk_sfpu/ckernel_sfpu_rand.h:30-100`).
- Seeds: per-core seed = `seed + core_idx + device_seed_offset` when `seed != 0`; when `seed == 0` each core draws from a host RNG (non-reproducible; the doc's "defaults to 0" really means random): `OP/rand/device/rand_program_factory.cpp:25-28, 97` (re-verified: `attrs.seed != 0 ? attrs.seed + i + device_seed_offset : get_random_seed()`). Tile-offset stream separation `seed + stream_id*0x9E3779B9` (`tt_metal/hw/inc/api/compute/eltwise_unary/rand.h:40-48`). A nonzero seed reproduces for the same shape; a different seed does not grow the cache (`test_rand.py:175-221`).
- Mesh: `rand` builds one program per coordinate (`rand_program_factory.cpp:129-133`); `device_seed_offset` is nonzero only for `Shard` placements in `mesh_mapper` (`:66-82`, re-verified). With NO mapper a fixed seed gives IDENTICAL values on every chip; with `ttnn.MeshMapperConfig([ttnn.PlacementShard(dim)])` the chips get distinct values (tested `tests/ttnn/nightly/unit_tests/operations/rand/test_rand.py:358-420`). With `seed=0` on a mesh, each chip draws host seeds independently (inferred from `rand_program_factory.cpp:97`, untested).
- tt-train's `randn` op composes Box-Muller from two FLOAT32 `ttnn.rand` + `log`/`sqrt`/`cos` (`tt-train/sources/ttml/ops/randn_op.cpp:33-90`): a proven recipe, but `ttnn.randn` already does it in one kernel.

**Others:** `ttnn.uniform(input, from=0, to=1, seed=0, *, memory_config, compute_kernel_config)` fills an existing tensor in place (bf16/fp32 TILE; seed + core_idx or random if 0): `OP/uniform/uniform_nanobind.cpp:54-64`; `uniform_device_operation.cpp:13-24`; `uniform_program_factory.cpp:85-87`. `ttnn.bernoulli(input_probs, seed=0, *, output, dtype=None, ...)` (bf16/fp32 TILE in, default fp32 out; override ignores mesh coordinate: `OP/bernoulli/bernoulli_nanobind.cpp:55-65`; `bernoulli_program_factory.cpp:81-82, 230`). `ttnn.experimental.dropout(input_tensor, probability, scale, seed, *, use_per_device_seed=True, ...)`: documented bf16 TILE rank 2-4; per-device seed = seed + device id (`OP/experimental/dropout/dropout_nanobind.cpp:61-70`; `dropout_program_factory.cpp:44-53`); fp32 not verified. `ttnn.manual_seed(seeds=0, *, device=None, user_ids=None, sub_core_grids=None)` (`OP/reduction/manual_seed/manual_seed_nanobind.cpp:73-79`): `rand`/`randn` call `rand_tile_init(seed)` on every launch so it almost certainly does not affect them (inferred); for reproducibility pass `seed=` to each call.

**Verdicts (item 6):** `ttnn.randn` fp32 with an explicit per-call seed: **yes** (check per-chip decorrelation on a mesh and the trace-replay behavior). `ttnn.rand` fp32: **yes** (per-chip decorrelation needs a Shard `mesh_mapper` or `seed + chip_index`). `uniform`, `bernoulli`: yes. `dropout`: unclear. `manual_seed`: no. Note the project brief's parity mode (host torch generator for noise) avoids all of this.

**Gotchas (items 4-6):** (1) `full/zeros/ones/rand/randn` default to BFLOAT16 and `full/zeros` to ROW_MAJOR: always pass `dtype=ttnn.float32` (and layout). (2) A user `compute_kernel_config` defaults to `fp32_dest_acc_en=False`: it silently drops fp32 reductions to TF32 or makes std/var throw. (3) Rank-0 outputs of full reductions: downstream behavior of rank-0 TILE tensors was not checked; use `keepdim=True`. (4) `update_cache`/`fill_cache` Blackhole skips (#12349). (5) Not examined: `paged_*` fp32, `permute` fp32 test coverage, dropout fp32. (6) Mesh-seed conclusions for `randn`/`bernoulli` are derived from adapter code, not tests.

## 8. Trace

**Signatures (MeshDevice only; there are no single-device variants)**
- `ttnn.begin_trace_capture(mesh_device, *, cq_id=None) -> ttnn.MeshTraceId` (`ttnn/cpp/ttnn-nanobind/operations/trace.cpp:47-57`, re-verified).
- `ttnn.end_trace_capture(mesh_device, trace_id, *, cq_id=None)` (`:75-85`).
- `ttnn.execute_trace(mesh_device, trace_id, *, cq_id=None, blocking=True) -> None` (`:101-112`, re-verified). `cq_id=None` means the current CQ (`ttnn/cpp/ttnn/operations/trace.cpp:16-34`).
- `ttnn.release_trace(mesh_device, trace_id)` (`:129-134`). Also `ttnn.MeshTraceId` (`:29`), `ttnn.is_trace_capture_active(device)` (`ttnn/cpp/ttnn-nanobind/device.cpp:670-681`). Re-exports at `ttnn/ttnn/__init__.py:123-146`; with `TT_METAL_TRACE_ALLOC_TRACKING=1`, `execute_trace` is wrapped by the allocation checker.

**Requirements**
- **Trace region:** pass `trace_region_size` to `open_mesh_device`. The older report says a size is mandatory and a FATAL reports the needed size (`tech_reports/AdvancedPerformanceOptimizationsForModels/AdvancedPerformanceOptimizationsForModels.md:57-65`); in v0.81.1 the default 0 means dynamic top-down DRAM trace buffers validated against high-water marks (`tech_reports/AdvancedPerformanceOptimizationsForModels/TraceCorrectness.md:95, 163-168`). Tests use explicit sizes: 60000 (`test_multi_device_trace.py:24`), 500000 (`test_ccl_bandwidth.py:140`), 100_000_000 on BH Galaxy (`test_trace_exec_buf_end_race.py:16`), 268435456 for a TP model (`models/demos/blackhole/qwen36/tests/test_gdn_tp.py:894`). Size ours after measuring.
- **Warm up first:** all programs must already be in the program cache (`TraceCorrectness.md:44-49`; cache on by default `tt_metal/api/tt-metalium/program_cache.hpp:167`). A cache miss during capture is `TT_FATAL` "Cannot load new binaries during trace capture ... Warm up before capturing a trace" (`tt_metal/distributed/mesh_workload.cpp:195-200`, re-verified).
- **No host I/O or events inside capture:** writes, reads and event sync are all `TT_FATAL` (`fd_mesh_command_queue.cpp:616, 655, 703, 804, 851, 949, 1015`): this covers `from_torch(device=...)`, `copy_host_to_device_tensor`, `.cpu()`, `to_torch`, events.
- **Persistent buffers:** preallocate inputs and keep the outputs returned from the captured region alive; addresses are baked in (`AdvancedPerformanceOptimizationsForModels.md:81-90, 98-124`). Allocations INSIDE the capture are allowed (temporaries are baked at fixed addresses; replay does no allocator work, `TraceCorrectness.md:40`), but a buffer allocated after capture can alias them and be corrupted by replay (`TraceCorrectness.md:51-60`; hidden allocations such as a `reshape` lookup table or a program-cache buffer count, `:60`). `TT_METAL_TRACE_ALLOC_TRACKING=1` makes `execute_trace` raise on unsafe live buffers (`TraceCorrectness.md:82-95`); `ttnn/ttnn/tools/trace_allocation_tracker.py:326` `acknowledge_corruptible(tensor)` marks intentionally reused I/O buffers.
- **Non-blocking replay:** `execute_trace(..., blocking=False)` then an in-order read or `synchronize_device` is the documented pattern (`AdvancedPerformanceOptimizationsForModels.md:117-124`); the BH test does it with host writes between replays (`test_trace_exec_buf_end_race.py:44-48`).

**What cannot be captured / is not dynamic** (replay never re-runs Python or program factories)
- Python `if` branches and Python scalars are frozen (`TraceCorrectness.md:151-161`). Inference: an Adam learning rate, beta-power correction or any Python float passed to an op is baked at capture: feed such values as device tensors updated by `copy_host_to_device_tensor` (outside the trace).
- `ttnn.rand`/`ttnn.randn` seeds are per-core runtime args refreshed only in the cache-hit override path (`OP/rand/device/rand_program_factory.cpp:97, 199-205, 238-241`; `OP/randn/device/randn_program_factory.cpp:130-133, 152-165`): a replayed trace most likely emits identical noise each time. Sample noise outside the trace (host or separate eager op) and copy it into a persistent buffer. (Inference, Q16.)
- Host reads/writes, event sync and any op not yet in the program cache (above).
- `synchronize_device` inside a capture window: no explicit check found (event-sync fatals at `fd_mesh_command_queue.cpp:949, 1015`).

**Real multi-chip examples**
1. `tests/ttnn/unit_tests/base_functionality/test_multi_device_trace.py:24-117`: 1x8 mesh, preallocated mesh tensors, `ShardTensorToMesh` host staging, `copy_host_to_device_tensor`, non-blocking replay, readback via `ConcatMeshToTensor`; eltwise and matmul only, no CCL. Replicated weights via `ReplicateTensorToMesh` (`:231-239`).
2. `tests/nightly/t3000/ccl/test_all_gather.py:293-310`: compile, capture, replay `ttnn.all_gather` on a 1x8 mesh with persistent buffers; BH: `tests/ttnn/unit_tests/operations/ccl/blackhole_CI/box/nightly/test_minimal_reduce_scatter_async_bh.py:186-215` (ring, explicit semaphores and persistent buffers; comment at `:203-205`: "Rebind the cached program after capture; replay must retain each captured buffer/semaphore").
3. `models/demos/blackhole/qwen36/tests/test_gdn_tp.py:887-955`: BH 1x4 mesh, `FABRIC_1D`, a TP model including its CCLs captured once and replayed with `blocking=True`.
4. `tests/ttnn/unit_tests/benchmarks/test_ccl_bandwidth.py:263-320`: traces `ttnn.all_reduce`, `ttnn.reduce_scatter`, `ttnn.all_gather` after one eager warm-up; fp32 option (`:43, 94`).
5. `tests/ttnn/distributed/test_trace_exec_buf_end_race.py`: regression for a mesh trace-replay hang (#60817) seen on BH Galaxy with many host writes between replays; the fix is in this tree per the test header.

**Verdict (item 8): yes** (fp32 with persistent buffers, host-fed noise and device-resident scalars); CCL inside a trace is exercised on BH and on 1x8 meshes.

## 9. CCL (all_reduce / reduce_scatter / all_gather) and fabric

**High-level ops (no semaphores to pass)**
- `ttnn.all_reduce(input_tensor, *, cluster_axis=None, subdevice_id=None, memory_config=None, num_links=None, topology=None)`: `ttnn/cpp/ttnn/operations/ccl/all_reduce/all_reduce_nanobind.cpp:55-65`. Always Sum (forwards `ReduceType::Sum` to `experimental::all_reduce_async`: `ttnn/cpp/ttnn/operations/ccl/all_reduce/all_reduce.cpp:52`). Dtypes BFLOAT16, BFLOAT8_B, FLOAT32; layouts TILE, ROW_MAJOR (`all_reduce_nanobind.cpp:38-48`); the doc states "The reduction is performed in BFLOAT16; BFLOAT8_B inputs are up-cast ...; and FLOAT32 takes a dedicated reduction path. Input must be rank 2 or greater" (re-verified; how exactly fp32 is reduced is not spelled out, Q15). Rank < 2 inputs are unsqueezed and restored (`ttnn/cpp/ttnn/operations/experimental/ccl/all_reduce_async/all_reduce_async.cpp:164-182, 330-350`; test `tests/nightly/t3000/ccl/test_all_reduce.py:225`).
  - `cluster_axis=None` on a flat 1xN mesh reduces across all devices; on a 2D mesh it chains axis 0 then axis 1 (`all_reduce.cpp:29-35`).
  - Two paths: reduce-scatter + all-gather (needs a dim divisible by num_devices, in tiles for the last two dims: `all_reduce_async.cpp:33-62, 375`), else composite all-gather + local sum; fp32 uses `local_sum_float32` = reshape/transpose/`ttnn.sum` (comment "moreh sum does not support float32 datatype", `all_reduce_async.cpp:103-150, 425-431`; `ttnn.sum` defaults to fp32 accumulation, item 4). ### 10.2 How the mesh layout is decided (this decides whether a tray subset works)

1. UMD discovery sees only the visible chips (item 11). Metal classifies the cluster from the UMD cluster descriptor: all chips the same board type; `BoardType::UBB_BLACKHOLE` => `ClusterType::BLACKHOLE_GALAXY` irrespective of chip count (`tt_metal/llrt/tt_cluster.cpp:126-135, 213-215`). Eight visible UBB chips are therefore still classified as `BLACKHOLE_GALAXY`, and `cluster.is_ubb_galaxy()` is true. Caveat: only `UBB_BLACKHOLE` is tested there; UMD also knows a `UBB_BLACKHOLE_CF` board type (board UPI 0x202; `umd/tt-umd/api/tt-umd/types/cluster_descriptor_types.hpp:37, 220`) that this classification does not map, so on an all-`_CF` host the cluster type would stay INVALID. Which variant this Galaxy reports is unknown (Q1 records the cluster-type log line).
2. Mesh graph source (`tt_metal/impl/context/metal_env.cpp:519-567`):
   - If `TT_MESH_GRAPH_DESC_PATH` is set (`tt_metal/llrt/rtoptions.cpp:609-616`), that `.textproto` is used (the file must exist or `TT_FATAL`, metal_env.cpp:522-526).
   - Else, if the distributed world size is 1 (a plain single process, no `mpirun`/`tt-run`): AUTO-DISCOVERY, i.e. "Constructing control plane using auto-discovery (no mesh graph descriptor)" (metal_env.cpp:531-534, 591-612). `ControlPlane::init_control_plane_auto_discovery` (`tt_metal/fabric/control_plane.cpp:613-690`) builds a physical system descriptor from the discovered chips and infers the biggest mesh that fits (`TopologyMapper::generate_mesh_graph_from_physical_system_descriptor`, `tt_metal/fabric/topology_mapper.cpp:1689-1830`). Candidate shapes come from `generate_possible_cluster_shapes` (`topology_mapper.cpp:1631-`): for 8 chips the first candidate is 4x2 which is explicitly rewritten to **2x4** (line 1654-1658), 1D shapes (8x1) are tried last. Fabric type candidates are tried most- to least-connected (torus => mesh) (topology_mapper.cpp:1753-1770); if a requested shape cannot be realized it silently downgrades and logs a warning (1825).
   - Else (world size > 1, no explicit path): default MGD by cluster type (`tt_metal/fabric/mesh_graph.cpp:112-146`; `BLACKHOLE_GALAXY` -> `single_bh_galaxy_mesh_graph_descriptor.textproto`, an 8x4 = 32-chip mesh pinned to tray 1 asic 1, file `tt_metal/fabric/mesh_graph_descriptors/single_bh_galaxy_mesh_graph_descriptor.textproto:1-25`). That default would NOT fit 8 visible chips.
3. Galaxy corner pinning is applied only to meshes whose chip count is a multiple of 32 and that are not 1D (`control_plane.cpp:516-530, 660-672`; `tt_metal/fabric/topology_mapper_utils.cpp:49-90`), so a 2x4 or 1x8 mesh is not corner-pinned.
4. `TT_MESH_ID` / `TT_MESH_HOST_RANK`: if both unset, "this host is the only host in the system and owns all Meshes" (`control_plane.cpp:330-337`).

Conclusion for ONE 8-chip tray in ONE process (no MPI launcher): restrict UMD to the tray with `TT_VISIBLE_DEVICES` (item 11), do NOT set `TT_MESH_ID`, optionally set nothing for the MGD (auto-discovery should infer a 2x4 mesh), then `ttnn.open_mesh_device(ttnn.MeshShape(2, 4))` (or `ttnn.MeshShape(1, 8)` for the ring-ordered line). This path is inferred from source only; see "OPEN QUESTIONS" Q1-Q3. If auto-discovery picks something unexpected, the fallback is an explicit 8-chip MGD in `TT_MESH_GRAPH_DESC_PATH`: `tt_metal/fabric/mesh_graph_descriptors/p150_x8_mesh_graph_descriptor.textproto:1-10` is a plain `arch: BLACKHOLE`, `dims: [2, 4]`, `channels { count: 2 policy: RELAXED }` single mesh (the physical tray is a 4x2 grid and a 2x4 mesh is isomorphic: comment in `single_bh_galaxy_4x4x2_z_graph_descriptor.textproto:1-23`).

### 11.2 PRECISE ID-SPACE ANSWER

**An integer token in `TT_VISIBLE_DEVICES` is NOT the `/dev/tenstorrent/N` number.** It is a 0-based index into the list of present `/dev/tenstorrent/N` nodes **sorted by PCI BDF string** (lowercase `dddd:bb:dd.f`, ascending). The code:

1. `get_bdf_to_device_id_map()` returns a `std::map<std::string,int>` of BDF -> N, built by opening every `/dev/tenstorrent/N` and reading its BDF (`pci_device.cpp:1188-1201`; entries whose read throws are silently skipped, lines 1193-1198).
2. `enumerate_devices()` iterates that map (hence BDF order) into `all_device_ids` (`pci_device.cpp:265-271`), and for an integer token `i` does `all_device_ids[i]` (`pci_device.cpp:304-325`); out of range throws (309-317). The selected set is then returned sorted by BDF (`pci_device.cpp:338-342`, `345-367`).
3. Chip numbering inside the process: local chips get UMD logical chip ids 0,1,2,... in `enumerate_devices()` order (`umd/tt-umd/src/topology/topology_discovery.cpp:288-327` with `get_next_chip_id()` at `umd/tt-umd/api/tt-umd/topology/topology_discovery.hpp:184-186`). Hence: for an unfiltered Galaxy, integer `i` == UMD logical id `i` == i-th BDF-sorted node. After filtering, the visible chips are renumbered 0..K-1 in BDF order, and those are the ids metal/ttnn see (`ttnn.get_device_ids() == [0..K-1]`, `distributed.py:639-641`; `physical_device_ids` in `open_mesh_device`).
4. Independent confirmation from tt-metal's own test code: "UMD now interprets TT_VISIBLE_DEVICES integers as logical IDs (BDF-sorted indices), not PCI device IDs. The cluster descriptor's chip_id is the logical ID; chips_with_mmio maps chip_id (logical) -> pci_device_id." (`tests/tt_metal/tt_fabric/physical_discovery/test_physical_system_descriptor.cpp:429-433`, again at 463 and 286). UMD changelog 0.9.3: "TT_VISIBLE_DEVICES uses logical IDs." (`umd/CHANGELOG:108`). And a worked example where the two spaces differ: "`Opening local chip ids/PCIe ids: {0..7}/[2,3,1,0,6,7,5,4]` on an 8-chip p150b host, where UMD chip 0 is `/dev/tenstorrent/2`" (`tt_metal/fabric/experimental/x280/README.md:696-701`; it also says "`TT_VISIBLE_DEVICES` and `tt-smi -r` take UMD chip ids; `/dev/tenstorrent/N` takes PCIe ids").

**Documentation contradictions (treat the code as authoritative):**
- `tech_reports/Programming_Mesh_of_Devices/Programming_Mesh_of_Devices_with_TT-NN.md:147,171` claims device IDs "matching `/dev/tenstorrent/<id>`" and that WH T3K PCIe ids are 0-3 (true there only because the BDF order equals the numeric order). `tech_reports/Programming_Multiple_Meshes/Programming_Multiple_Meshes.md:354` says "zero-indexed based on their PCIe enumeration order" (closer to the truth). Stale for a Galaxy.
- `umd/docs/TT_VISIBLE_DEVICES.md:54-66` says the integer is "the position in the sorted list of PCI device IDs (i.e., the files under /dev/tenstorrent/)" and "not the UMD logical ID", with a note that the proposal is to align with logical ids. The code sorts by BDF (not by numeric N), so on any host where BDF order != numeric order the doc is wrong. `umd/docs/TT_VISIBLE_DEVICES.md:15-19,32` also states "PCI IDs are not stable across reset" while logical ids are sorted by BDF and stable.
- Whether the 8 nodes `/dev/tenstorrent/16..23` occupy BDF-sorted positions 16..23 on this host is UNKNOWN. It must not be assumed.

**BDF tokens (the unambiguous way):** a token is a BDF if it contains `:` or `.` and only hex digits/`.`/`:` (`umd/tt-umd/src/common/utils.hpp:85-88`). Matching is a case-sensitive SUBSTRING `find` against the lowercase BDF (`pci_device.cpp:279-293`), so a full BDF selects exactly one chip, a prefix such as `0000:c` selects every chip whose BDF contains it (doc example, written for a WH 6U tray: `TT_VISIBLE_DEVICES.md:78-82,124-125`), and a token that matches nothing throws (`pci_device.cpp:295-299`), i.e. a typo fails closed. Integers and BDFs can be mixed and are deduplicated (`pci_device.cpp:273`, `TT_VISIBLE_DEVICES.md:86-92`). Empty string => zero devices (`pci_device.cpp:258-261`); unset => ALL devices (`253-256`).

How to get the BDF of `/dev/tenstorrent/N` without opening the node: sysfs `/sys/class/tenstorrent/tenstorrent!N/device` is a symlink whose basename is the BDF (pattern used in `tools/scaleout/kmd_triage/device_side.sh:270-273`; reverse direction `/sys/bus/pci/devices/<bdf>/tenstorrent/tenstorrent!*` in `umd/tt-umd/src/warm_reset.cpp:148`). I did NOT read sysfs (read-only source survey; it also needs the owner's OK under the brief's "no queries of other chips" rule even though it is host PCI metadata). Recommended: obtain BDFs of exactly `/dev/tenstorrent/16..23` that way, put them in `scripts/tray_env.sh` as `ALLOWED_PCI_BDFS`, set `TT_VISIBLE_DEVICES` to the 8 full BDFs.

### 11.3 Are chips NOT listed still opened/touched?

(File-name shorthand in 11.3: `topology_discovery.cpp` and `topology_discovery_blackhole.cpp` are in `umd/tt-umd/src/topology/`, `pci_device.cpp` is `umd/tt-umd/src/pcie/pci_device.cpp`, `tt_cluster.cpp` is `tt_metal/llrt/tt_cluster.cpp`.)

Answer: **NOT initialized, but their device nodes ARE opened (briefly) by UMD's enumeration.** Detail:

A. What is NOT done for unlisted chips (good): no `TTDevice::create`, no BAR/TLB mapping, no ARC/ETH/NOC reads or writes, no firmware, no reset. Discovery creates devices only for ids returned by the filtered `enumerate_devices()` (`topology_discovery.cpp:288-306`). Blackhole remote ASICs seen over ethernet are not instantiated: a remote ASIC not in the local discovered set is only recorded as an `ethernet_connections_to_remote_devices` entry (`topology_discovery.cpp:440-453`; on UBB trays the board id is deliberately replaced by the ASIC id so the filter works at chip granularity: `topology_discovery_blackhole.cpp:63-72`, `is_running_on_6u` at 182). Cluster-type detection, the physical system descriptor and the control plane all work from the cluster descriptor of the visible chips only (`tt_cluster.cpp:282-284` passes the already-discovered `get_cluster_desc()`; `tt_metal/fabric/physical_system_discovery.cpp` reads only `cluster`/`cluster_desc` chips).

B. What IS done to unlisted chips (the catch): `PCIDevice::enumerate_devices()` calls `get_bdf_to_device_id_map()` three times when `TT_VISIBLE_DEVICES` is set (`pci_device.cpp:265`, `269`, and via `sort_ids_based_on_bdf` at `342` -> `347`) and once when it is unset (`255` -> `347`), and each call runs `read_device_info()` on EVERY `/dev/tenstorrent/N` (`pci_device.cpp:1188-1201`), which does `tt_device_open(path, ..., O_APPEND)` (`pci_device.cpp:182`) = `open(path, O_RDWR | O_CLOEXEC | O_APPEND)` (`umd/tt-kmd-lib/src/tt_kmd_lib.c:76-94`), a `TENSTORRENT_IOCTL_GET_DEVICE_INFO` ioctl (`tt_kmd_lib.c:104-110`), and `tt_device_close`. With `TT_VISIBLE_DEVICES` unset the same all-nodes pass happens (line 255) and then every chip is fully opened and initialized. This pass is repeated by several callers: `probe_bus_architecture` -> `enumerate_devices_info()` (`topology_discovery.cpp:71-79`), `get_connected_devices` (`291`), `fill_cluster_descriptor_info` (`510`), `tt_metal/llrt/get_platform_architecture.hpp:28`, `tt_metal/distributed/pcie_core_writer.cpp:21`. The only case with zero opens is `TT_VISIBLE_DEVICES=""` (empty), which returns before building the map (`pci_device.cpp:258-261`).
   - Consequence 1: a post-open `/proc/self/fd` inspection (the brief's rule 2-2b) will see only the allowed nodes (the probe fds are closed), so it passes, but it does NOT prove that no other node was ever opened.
   - Consequence 2 (kernel-side, NOT in this tree): a comment in `tt_metal/fabric/experimental/x280/include/x280/device/x280_runtime.hpp:56-58` states that "tt-kmd sends [a power-setting message] on every open() of /dev/tenstorrent/N (tt_cdev_open -> tenstorrent_set_aggregated_power_state)". If accurate, merely opening an unlisted node makes the driver message that chip's firmware. I cannot verify this from source in the tree (tt-kmd is not vendored). Treat as probable.
   - Consequence 3: if any unlisted node cannot be opened (EACCES) or its info read throws, it is silently dropped from the map (`pci_device.cpp:1193-1198`). This is a usable isolation lever: make all other nodes un-openable for our user (ACL/permissions) or do not expose them (container with only `/dev/tenstorrent/16..23` bind-mounted; `TT_VISIBLE_DEVICES.md:138-139` describes the container case). Then the VFS rejects the `open()` before it reaches tt-kmd. Caveat: with integer tokens the indices then shift to "positions among accessible nodes" (a reason to use BDF tokens). These are recommendations for the owner (they need privileges we must not use); not verified.

C. Ordering hazards: the env var must be set before the first call that creates the cluster (`ttnn.open_mesh_device`, `ttnn.get_num_devices()`, anything that builds `MetalContext`); it is read via `getenv` each time (so `os.environ[...]` before first use works), but set it in the launching shell (the tech report advises "before importing ttnn": `Programming_Multiple_Meshes.md:673`). tt-run auto mode runs a discovery binary under the parent env and drops `TT_VISIBLE_DEVICES` from rank pass-through (`ttrun.py:1652-1667`); avoid tt-run auto mode on the shared host.

D. Other facts: UMD also sets BUSY power state on every chip it does open (`topology_discovery.cpp:307-316`; currently a no-op per the comment). `PCIDevice::get_all_device_ids()` ignores the variable (`pci_device.cpp:1168-1186`).

**Summary of item 11:** (1) Use BDF tokens, never bare integers, for the 8 allowed chips; integers are BDF-sorted indices, not `/dev` numbers. (2) `TT_VISIBLE_DEVICES` guarantees that only the listed chips are initialized/used, but UMD still opens-then-closes every `/dev/tenstorrent/*` node during enumeration, and tt-kmd (per a source comment) messages the chip on open. A hard "never opened" guarantee needs OS-level isolation of the other nodes (container or permissions). (3) `TT_METAL_VISIBLE_DEVICES` is a dead variable. (4) Mark as AMBIGUOUS/UNVERIFIED: the BDFs of nodes 16..23, kmd behavior on open, and whether the BDF order of this host equals the numeric order (Q5-Q7).
