| S34 Mini-batch partition and short last batch | `batch_size = N*T`; requires `1 <= num_mini_batches <= batch_size` else `ValueError`. ## RISKS / SURPRISES (things that would trip up a hardware re-implementation)

Ordered by expected impact.

1. BRIEF mismatch: `max_grad_norm` is PER MODEL, not joint. `BRIEF.md` 3.7 says "max_grad_norm over actor+critic as a whole"; upstream runs two
   independent `clip_grad_norm_` calls (`ppo.py:309-310`), actor (including the std parameter) and critic separately. A joint device-side norm
   would be a silent semantic change. Needs an explicit decision (match upstream, i.e. two norms).
2. Time-out bootstrap uses the PRE-step value `V(s_t)`, not the next-state value (`ppo.py:154-158`). It is added to the stored reward before
   GAE, and `done` stays 1. This is a known approximation and must be replicated exactly, including that `V(s_t)` is the value recorded by `act`.
3. One `randperm` per `update()`, reused by all epochs (`rollout_storage.py:232,243-248`); mini-batch `i` is a contiguous slice of that
   permutation; rows are addressed time-major (`i = t*N + n`). A re-implementation that reshuffles per epoch changes the learning dynamics.
   The permutation is drawn lazily at the first `next()`, after the rollout noise, so RNG order is "all noise first, then the permutation".
4. Adaptive LR is evaluated at EVERY mini-batch and compounds (S17), with hard-coded bounds 1e-5 / 1e-2 that also clamp in the "wrong" direction
   (S16). It uses the KL of the CURRENT forward against the stored rollout parameters, before that mini-batch's step. On the first mini-batch
   of an update the policy has not changed, so `kl_mean` is ~0: if it is exactly 0.0 the `> 0.0` guard suppresses the increase, but if it is
   a tiny positive number (very likely whenever the rollout forward and the mini-batch forward are not bit-identical, e.g. different batch
   sizes or kernels) the LR is multiplied by 1.5. The LR trajectory is therefore sensitive to sub-ulp numerical differences and cannot be
   expected to match bitwise; parity tests should drive the rule with injected KL values (as `tests/algorithms/test_ppo.py:426-437` does)
   and compare LR trajectories statistically. The ratio at the first mini-batch is not guaranteed to be exactly 1 upstream either (upstream
   tests only check `atol=1e-6`, `tests/algorithms/test_ppo.py:316`); BRIEF 3.4's "same kernel path" requirement is stricter than upstream.
5. Multi-GPU LR is rounded through float32 after every evaluation (`ppo.py:260-262`); single device keeps a double. If the LR lives on device
   as a tensor it must be at least fp32 (a bf16 LR would be wrong), and the Python-float `learning_rate` attribute must still be readable by the
   runner each iteration (`on_policy_runner.py:123`).
6. Normalizer subtleties: `eps` is added to the std (`std + 1e-2`), initial transform is `x/1.01` (not identity), there is no clipping argument,
   `_std` is a re-assigned buffer, statistics are updated once per iteration AFTER the epochs from all `T*N` raw stored observations (so the whole
   iteration, including rollout and mini-batches, uses one frozen set of statistics) and updates are skipped in eval mode. In multi-device runs
   the collectives are keyed on `torch.distributed.is_initialized()` and produce GLOBAL statistics, whereas advantage normalization is rank-local.
7. Advantages: recomputed as `returns - values` (not the running GAE variable), normalized with unbiased std and `+1e-8` outside; global over the
   whole local rollout by default. Per-mini-batch normalization is an option that works on the batch copy only.
8. `get_policy()` is called EVERY iteration by the runner just to log `output_std` (`on_policy_runner.py:124`). If `get_policy()` builds a torch
   mirror by downloading device weights, this becomes a per-iteration full weight readback; cache or implement `output_std` cheaply. Also
   `get_inference_policy(device)` calls `.to(device)` on the live policy IN PLACE and switches the whole algorithm to eval mode, and `output_std`
   reads the STORED distribution, which exists only after at least one stochastic forward (it raises `AttributeError` on a fresh model).
9. Storage allocates and copies EVERY observation group the env returns, not only the groups used by actor/critic (`rollout_storage.py:142-148`,
   `:180`); `distribution_params` stores the std per sample `[T,N,A]` although it is state-independent. Optimization room, but the reference
   buffers have these shapes.
10. Parameter order defines optimizer-state indices in checkpoints: actor params (`distribution.std_param` FIRST, because the distribution is
    registered before the MLP, `mlp_model.py:66-76`), then critic params, de-duplicated. `learn_std=False` parameters stay in the list. A
    device-side optimizer that wants bidirectional checkpoint compatibility must reproduce this order and the torch `state_dict` structure.
11. Weight init: `MLP.init_weights` (orthogonal) is never called; initialization is torch's default `nn.Linear` init and the Gaussian
    `init_mlp_weights` is a no-op. The models are constructed (consuming the RNG) before the algorithm (`ppo.py:449,453`). Reusing
    `PPO.construct_algorithm` reproduces the exact initial weights for a given seed.
12. Inference mode: `act`, `process_env_step`, `compute_returns` run under `torch.inference_mode()` (`on_policy_runner.py:83-106`), `update` does not.
    Any host-side torch staging buffer that is created inside the first block and modified in place in `update` hits "in-place update of an
    inference tensor outside inference mode" [TORCH]; allocate such buffers outside the block.
13. Host syncs in upstream: `.item()` of three losses per mini-batch (`ppo.py:317-319`), `check_nan` (default on) every step
    (`on_policy_runner.py:90`), `alg.learning_rate` and `output_std` every iteration. A "one sync per step" target
    must account for `check_nan` operating on env-side tensors (host or env device), which is outside the TT algorithm.
14. Resume is off by one (saved `iter` is re-run, `on_policy_runner.py:77,168`); `torch.load(..., weights_only=False)` is a pickle load;
    `map_location` defaults to None, so a CUDA-saved Isaac Lab checkpoint needs `map_location="cpu"` on a TT host. RNG state is not part of a
    checkpoint.
15. cfg handling: unknown keys in `algorithm`, `actor`, `critic`, `distribution_cfg` raise `TypeError` unless the TT class takes `**kwargs`;
    when `PPO.construct_algorithm` is reused the TT constructor ALWAYS receives `rnd_cfg`, `symmetry_cfg`, `multi_gpu_cfg` and
    `grad_reduce_bucket_mb`-compatible kwargs and `alg.compile(...)` is always called (`ppo.py:460,463`; `rnd.py:241`; `symmetry.py:136`).
    The runner mutates the caller's cfg (`cfg["multi_gpu"]`, `cfg["obs_groups"]`). A bare class name is not resolvable for a plugin package
    (`utils.py:167-176`): use `"rsl_rl_tt.<module>:Class"`.
16. Numerics with no safety nets: no clamp on `exp(logp_new - logp_old)` (can overflow with bf16 or approximate exp), no value-target
    normalization, the value clip uses the policy `clip_param`, the value loss has no 0.5 factor, entropy gradient reaches only the std
    parameter, clamped std entries get zero gradient. `Normal.set_default_validate_args(False)` disables argument validation globally.
17. Time-major flatten and the final `last_values` use the post-reset observation of the last step for envs that finished at `T-1`; the
    `dones[T-1]` mask must be applied (S02/S03). `dones` is stored as uint8; `time_outs` and `dones` are separate signals and `time_outs` is
    assumed to be a subset of `dones` by the caller (nothing in upstream enforces it).
18. Multi-process mode is hard-wired to NCCL/CUDA (`on_policy_runner.py:215-257`); a single-process multi-chip TT design keeps `WORLD_SIZE`
    unset, so `cfg["multi_gpu"] = None` and the logger's fps counts only one process's `N`.
